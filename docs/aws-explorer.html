Deployment topology

One custom VPC, three availability zones, three subnet tiers.

This is the same app you saw in the overview — a Next.js frontend, Python FastAPI + LangGraph, and Go microservices — placed into a production-shaped AWS network. Everything below is laid out the way AWS draws it: zones across the top, network tiers down the side. Start with the concepts, then click a service.

Region → AZ Where it physically runs

An Availability Zone is one or more isolated data centers with independent power and network. We use three (1a / 1b / 1c) so one zone failing never takes the app down.

Subnet tier A slice of the network

A subnet is a range of IPs that lives in exactly one AZ. We group them by job: public (reachable from the internet), private-app (compute), private-data (databases) — repeated in every AZ.

Security group A per-resource firewall

A security group is a stateful allow-list wrapped around a resource. It names exactly who may connect and on which port. We give each service its own, so the ledger can't be reached by anything except the services that need it.

Your question

“Do we just use the default VPC?” — No. The default VPC puts every resource in public subnets in a flat network. Instead we build a custom VPC and split it into public / private-app / private-data subnets spread over 3 AZs. Databases get no route to the internet at all; only the load balancer is public. That separation is the whole point of the design.

Why it's shaped this way

The Well-Architected trade-offs

AWS's Well-Architected Framework is five lenses for judging a design. Here's how each one shows up in the choices above — the reasoning a beginner is usually missing.

🛡️ Security

  • Private by default — only the ALB is public; data subnets have no internet route.
  • Least-privilege SGs — each service SG names its exact callers & ports.
  • IRSA + Secrets Manager — pods get scoped IAM roles, no long-lived keys; .env never committed.
  • KMS + TLS — encrypted at rest and in transit; WAF/Shield at the edge.

🔁 Reliability

  • 3 AZs — subnets, nodes, and brokers are replicated per zone.
  • Multi-AZ failover — Aurora reader & RDS standby promote automatically.
  • MSK RF=3 + per-topic DLQ so a poison record never blocks a partition.
  • HPA + KEDA — pods scale on CPU; the fraud worker scales on Kafka lag.

⚡ Performance

  • Graviton (m7g/m6g) — better price/performance per vCPU.
  • CloudFront caches static/ISR at the edge, near users.
  • Serverless data — Aurora v2 & MSK Serverless track load automatically.
  • Right-sized requests — pods request only what they use, so nodes pack densely.

💰 Cost

  • Pay-per-use data tiers — no idle broker/DB capacity in dev.
  • VPC endpoints + S3 gateway (free) slash NAT data-processing charges.
  • Spot nodes for stateless pods; on-demand for stateful.
  • 1 NAT for dev, per-AZ NAT only in prod where HA is worth it.

🛠️ Operational excellence

  • Infra as code — VPC, EKS, and data tiers in Terraform / eksctl.
  • GitOps — your existing GitHub Actions deploys via an OIDC role to ECR/EKS.
  • One observability plane — OTLP → AMP + Managed Grafana + X-Ray (ADOT).

🌱 Sustainability

  • Graviton draws less power for the same work.
  • Serverless & autoscaling release capacity when idle instead of running hot 24/7.
  • Consolidated regions — keep data & compute co-located to avoid cross-region transfer.
