# Secrets Management Runbook

Every runbook so far has put credentials into the cluster one of two ways:
by hand (`kubectl create secret`, the Kubernetes runbook) or generated by
Terraform and written straight into state (the Terraform runbook, section 6).
Both work on a laptop. Neither is something you could push to GitHub: the
first never touches git at all, and the second puts plaintext passwords in a
state file. This runbook covers three ways to keep credentials **in git**,
readable by anyone with repo access, useless to them because the values are
encrypted or absent, and readable in the clear only inside the cluster.

It follows the same format as the other runbooks. Every numbered section
states a goal, the commands, why each step exists, and how to check it
worked. Complete sections 2, 3 and 4 of
[`k8s-deployment-runbook.md`](./k8s-deployment-runbook.md) first: tools
installed, kind cluster running. You do not need the Helm release or Argo CD
running to follow sections 4 to 9 below; sections 10 to 13 assume Argo CD is
installed, as in [`argocd-runbook.md`](./argocd-runbook.md).

## What you will end up with

Three independent, swappable ways of getting `enjoythings-secret` into the
`enjoythings` namespace, each demonstrated end to end:

1. **Sealed Secrets** — encrypt a Secret on your laptop with a public key, and
   only the cluster's private key can decrypt it. The ciphertext lives in git;
   Argo CD syncs it like any other manifest.
2. **External Secrets Operator (ESO) + Vault dev mode** — nothing about the
   credential lives in git at all. A controller inside the cluster pulls
   values from Vault (standing in for AWS Secrets Manager, GCP Secret
   Manager, or a real Vault cluster) and keeps the Secret in sync.
3. **SOPS with age** — encrypt the Helm values file itself, commit the
   encrypted file, and decrypt it just before `helm upgrade` using the
   `helm-secrets` plugin. The chart renders its own Secret, as in the plain
   Kubernetes runbook.

```
services/k8s/secrets/
├── sealed-secrets/   controller values, plaintext template, seal.sh, the committed SealedSecret
├── external-secrets/ ESO values, Vault dev values, SecretStore, ExternalSecret, seed script
└── sops/             .sops.yaml, age key setup script, example values file
```

Optionally, `infra/terraform/26-secrets/` installs the three controllers
(Sealed Secrets, ESO, Vault dev) with the Helm provider, the same way stage 20
installs Argo CD. It does not create the SealedSecret, SecretStore or
ExternalSecret custom resources themselves — those need CRDs the Helm
releases only just installed, so they are applied by hand or by Argo CD, the
same division stage 30 already uses for the Application resource.

By the end you will have rotated a credential twice — once by re-sealing a
SealedSecret, once by changing a value in Vault and watching ESO rewrite the
Secret live — and you will know exactly which of the three approaches fits a
given team and cloud.

## 1. Vocabulary you need

| Term | What it is |
| --- | --- |
| **Envelope encryption** | Encrypt the data with a random one-time key, then encrypt only that key with your real key. Sealed Secrets and age both work this way; it is why sealing the same value twice gives different ciphertext. |
| **Asymmetric keypair** | A public half that only encrypts and a private half that only decrypts. Sealed Secrets and age both use one. Anyone may have the public key; only the cluster (Sealed Secrets) or you (age) may have the private key. |
| **SealedSecret** | A custom resource holding ciphertext. The Sealed Secrets controller decrypts it into an ordinary `Secret` inside the cluster and keeps them in sync. |
| **kubeseal** | The CLI that encrypts a plaintext `Secret` into a `SealedSecret`, talking to the controller (or an offline certificate) for the public key. |
| **Scope (`strict`/`namespace-wide`/`cluster-wide`)** | How tightly the ciphertext is bound. `strict`, the default and what this runbook uses, binds it to one name in one namespace: copying the YAML elsewhere produces garbage. |
| **External secret store** | Wherever the real credential lives: Vault, AWS Secrets Manager, GCP Secret Manager. Never git. |
| **SecretStore / ClusterSecretStore** | ESO's custom resource describing how to reach one external store and authenticate to it. Namespaced vs. cluster-wide. |
| **ExternalSecret** | ESO's custom resource: which keys to pull from which SecretStore, and the Kubernetes `Secret` to keep in sync. |
| **refreshInterval** | How often ESO re-reads the store and rewrites the Secret if anything changed. This is what makes rotation automatic. |
| **Vault dev mode** | A single Vault server, in-memory, auto-unsealed, wiped on every restart. Never production; a free stand-in for a managed secret store here. |
| **KV v2 secrets engine** | Vault's versioned key-value store. `vault kv put` writes a version; `vault kv patch` changes one field without touching the others. |
| **age** | A small, modern asymmetric encryption tool. A public key starts `age1...`; a private key (identity) starts `AGE-SECRET-KEY-1...`. |
| **SOPS** | Mozilla's "Secrets OPerationS": encrypts specific fields inside a structured file (YAML/JSON/etc.), leaving the rest readable, using any of several key backends (age, PGP, cloud KMS). |
| **helm-secrets** | A Helm plugin that wraps `helm` subcommands, transparently decrypting a SOPS-encrypted values file with `sops` before handing it to Helm, so `helm secrets upgrade` reads exactly like `helm upgrade` with one extra word. |
| **Ownership (of a Kubernetes object)** | Whichever controller last wrote an object's spec and expects to keep doing so. Two controllers both trying to own `enjoythings-secret` fight forever, each reverting the other's write. |

## 2. The Secret contract, and who is allowed to own it

### Goal

Understand exactly what every approach below has to produce, and why only one
thing may own it at a time.

### Steps

```sh
cat services/charts/enjoythings/templates/secret.yaml
```

### Why

The chart's Deployments read six environment variables via `envFrom` a
`Secret` named **`enjoythings-secret`** in namespace **`enjoythings`**, with
exactly these keys:

| Key | Used by |
| --- | --- |
| `JWT_SECRET` | Every service that verifies or issues a token. |
| `POSTGRES_PASSWORD` | The main Postgres container and any service connecting directly. |
| `FRAUD_POSTGRES_PASSWORD` | The fraud TimescaleDB container and the fraud worker. |
| `DATABASE_URL` | Services connecting to the main database. Contains `POSTGRES_PASSWORD` inline — the two must always agree. |
| `FRAUD_DATABASE_URL` | The fraud worker's connection string. Contains `FRAUD_POSTGRES_PASSWORD` inline. |
| `LOCAL_LLM_API_KEY` | The AI agent, when pointed at a hosted LLM instead of a local one. |

The chart's `secrets.create` value chooses who renders this object:

- `true` (the default): the chart itself renders it from `values.yaml`, which
  is how the plain Kubernetes runbook and the SOPS approach (section 12) work.
- `false`: something else creates it — kubeseal's controller, or ESO. The
  chart then only *reads* the Secret; it never writes it.

**Only one thing may own `enjoythings-secret` at a time.** `infra/terraform/20-platform`
creates it too, with `secrets.create=false` and generated `random_password`
values — exactly the shape Sealed Secrets and ESO also produce. If you have
run through the Terraform runbook, that stage's `kubernetes_secret_v1.app`
resource already owns this object. Before letting Sealed Secrets or ESO own
it, remove Terraform's copy:

```sh
terraform -chdir=infra/terraform/20-platform destroy -target=kubernetes_secret_v1.app
```

Skipping this is not cosmetic: Terraform's refresh notices the Secret's
contents "changed" relative to its plan and overwrites them with its own
generated passwords on the next `apply`, silently pulling the rug out from
under running pods. Two owners of one object is a bug class, not a
preference — pick exactly one path below per environment.

### Check

You can name the six keys from memory, and you can say which of Terraform,
Sealed Secrets, ESO or the chart's own `secrets.create=true` currently owns
`enjoythings-secret` in your cluster.

## 3. Install the tools

### Goal

`kubeseal`, `age`/`age-keygen`, and `sops` on your machine. `helm` and
`kubectl` already exist from the Kubernetes runbook.

### Steps

```sh
brew install kubeseal age sops
kubeseal --version   # v0.39.1
age --version        # v1.3.2
sops --version        # 3.13.3
```

### Why

- `kubeseal` is the client half of Sealed Secrets; only it can talk to the
  controller's public key. The controller itself is installed later, by Helm.
- `age` provides both `age-keygen` (make a keypair) and `age` (encrypt/decrypt
  a file by hand, not needed for the workflow below but useful for
  inspection). SOPS calls into the same key format without shelling out to
  the `age` binary, but installing it lets you generate and inspect keys with
  the standard tool.
- `sops` is the single binary that does the encrypting; the `helm-secrets`
  plugin (section 12) shells out to it.

### Check

All three version commands print a version with no error. These versions are
current stable releases as of this writing; a newer patch release is safe to
use.

## 4. Install the Sealed Secrets controller

### Goal

The controller running in `kube-system`, holding a keypair it generated
itself.

### Steps

```sh
helm repo add sealed-secrets https://bitnami.github.io/sealed-secrets
helm repo update
helm install sealed-secrets sealed-secrets/sealed-secrets \
  --version 2.19.3 --namespace kube-system \
  -f services/k8s/secrets/sealed-secrets/values.yaml --wait
kubectl get pods -n kube-system -l app.kubernetes.io/name=sealed-secrets
```

### Why

- Chart `sealed-secrets` version `2.19.3` installs controller image `0.39.1`,
  matching the `kubeseal` CLI version from section 3. Client and controller
  versions can drift a little, but keeping them equal avoids surprises in
  the sealed-secret format.
- `services/k8s/secrets/sealed-secrets/values.yaml` sets
  `fullnameOverride: sealed-secrets-controller`. Without it the chart names
  the controller Deployment and Service after the Helm release
  (`sealed-secrets`), but `kubeseal` looks for a controller named
  `sealed-secrets-controller` in `kube-system` by default. The override means
  every `kubeseal` command in this runbook needs no extra flags.
- The controller generates its own asymmetric keypair on first start and
  keeps the private half only in a Secret inside the cluster. It never
  leaves. `kubeseal` fetches the public half over the Kubernetes API (or you
  fetch it once and use it offline — section 5).

### Check

```sh
kubectl get pods -n kube-system -l app.kubernetes.io/name=sealed-secrets
```

shows one pod `Running`. `kubeseal --controller-name sealed-secrets-controller
--controller-namespace kube-system --fetch-cert` prints a PEM certificate with
no error — proof the CLI can find the controller under the name it assumes by
default.

## 5. Seal the application Secret

### Goal

`services/k8s/secrets/sealed-secrets/manifests/enjoythings-sealedsecret.yaml`
holding ciphertext your controller can decrypt.

### Steps

```sh
cd services/k8s/secrets/sealed-secrets
cat enjoythings-secret.template.yaml   # read it — never apply this file directly
LLM_API_KEY=sk-your-real-key ./seal.sh
git diff manifests/enjoythings-sealedsecret.yaml
```

### Why

- `enjoythings-secret.template.yaml` is the plain Secret shape with
  `REPLACE_ME_*` placeholders. It is never applied and never committed with
  real values — it exists purely as `seal.sh`'s input.
- `seal.sh` fills the placeholders from environment variables (random ones by
  `openssl rand` if you do not supply them), substitutes the same password
  into both the raw key and the connection URL so they cannot disagree, pipes
  the result straight into `kubeseal`, and writes only the ciphertext to
  `manifests/enjoythings-sealedsecret.yaml`. The plaintext exists only inside
  a shell pipe; nothing unencrypted touches disk.
- `--scope strict` (baked into `seal.sh`) binds the ciphertext to the exact
  name `enjoythings-secret` and namespace `enjoythings`. Copy the YAML to a
  different name or namespace and the controller refuses to decrypt it — the
  scope is part of what got encrypted, not a label you can edit afterward.
- The output is safe to commit. Reading it back out requires the
  controller's private key, which never leaves the cluster it was generated
  in. Losing the cluster means losing the ability to decrypt every
  SealedSecret ever sealed against it — see section 16 for backing that key
  up.
- `seal.sh` prints the generated `JWT_SECRET` once, to your terminal, because
  `cmd/devtoken` (used to mint local test tokens) needs the same value. This
  is the only moment the plaintext value is visible outside the pipe; treat
  your terminal scrollback accordingly.

### Check

`git diff` shows the six `encryptedData` values changed. `kubeseal
--validate < manifests/enjoythings-sealedsecret.yaml` (piped through
`--controller-name`/`--controller-namespace` as above) exits `0` if the
ciphertext round-trips against the current controller's key.

## 6. Deploy the SealedSecret with Argo CD

### Goal

Argo CD syncing the ciphertext into a real `enjoythings-secret`, with the
chart's own `secrets.create` switched off.

### Steps

Set `secrets.create: false` in the chart's values (see section 2), commit and
push both that change and the sealed manifest, then:

```sh
kubectl apply -f services/k8s/secrets/sealed-secrets/argocd-application.yaml
kubectl get application enjoythings-secrets -n argocd
kubectl get secret enjoythings-secret -n enjoythings -o jsonpath='{.data}' | jq keys
```

### Why

- `argocd-application.yaml` is a second, small Argo CD `Application` pointed
  at `services/k8s/secrets/sealed-secrets/manifests`, kept separate from the
  chart's own `Application` so the chart's manifest never has to change to
  accommodate secrets tooling — it just expects `secrets.create=false` and a
  Secret that already exists.
- Argo CD syncs whatever the SealedSecret controller has already decrypted
  into an ordinary `Secret`; Argo CD itself never sees plaintext, and its own
  diffing of a `SealedSecret` resource is happy comparing ciphertext to
  ciphertext.
- `resources-finalizer.argocd.argoproj.io` ensures deleting this Application
  also deletes the SealedSecret (and, once ESO or the chart claims it back,
  whatever depends on it) instead of leaving an orphan.

### Check

The Application shows `Synced`/`Healthy`. The Secret has the six expected
keys and `kubectl get secret enjoythings-secret -n enjoythings -o
jsonpath='{.metadata.ownerReferences}'` shows an owner reference back to the
SealedSecret.

## 7. Rotate a value with Sealed Secrets

### Goal

Change the JWT secret without touching anything but git.

### Steps

```sh
cd services/k8s/secrets/sealed-secrets
JWT_SECRET=$(openssl rand -hex 32) PG_PASSWORD=<same as before> \
  FRAUD_PASSWORD=<same as before> LLM_API_KEY=<same as before> ./seal.sh
git add manifests/enjoythings-sealedsecret.yaml
git commit -m "rotate JWT secret"
git push
kubectl rollout restart deployment -n enjoythings
```

### Why

Re-running `seal.sh` with one changed input re-encrypts all six values (the
script always re-seals the whole Secret; there is no partial-update mode).
Argo CD's automated sync picks up the new ciphertext, the controller
decrypts it, and the `Secret` object updates in place — pods that only read
the Secret as a volume would pick it up automatically, but `envFrom`
environment variables, which is how this chart consumes it, are only read at
container start. Nothing is broken; the rollout restart is simply required
to make already-running processes see the new value, exactly as it is for
the ordinary Kubernetes runbook.

### Check

`kubectl exec` into a pod and check the environment reflects the new value,
or watch old tokens signed with the previous secret start failing
verification.

## 8. Install External Secrets Operator and Vault in dev mode

### Goal

ESO and a throwaway Vault both running, ESO able to reach Vault.

### Steps

```sh
helm repo add external-secrets https://charts.external-secrets.io
helm repo add hashicorp https://helm.releases.hashicorp.com
helm repo update

helm install external-secrets external-secrets/external-secrets \
  --version 2.10.0 --namespace external-secrets --create-namespace \
  -f services/k8s/secrets/external-secrets/eso-values.yaml --wait

helm install vault hashicorp/vault --version 0.34.1 \
  --namespace vault --create-namespace \
  -f services/k8s/secrets/external-secrets/vault-values.yaml --wait

kubectl get pods -n external-secrets
kubectl get pods -n vault
```

### Why

- `eso-values.yaml` sets `installCRDs: true` so `SecretStore` and
  `ExternalSecret` exist as API kinds right after this install — the same
  reason Argo CD's CRDs have to land before the `Application` kind can be used.
- `vault-values.yaml` turns on `server.dev.enabled`: a single Vault server,
  auto-initialized and auto-unsealed, in-memory storage, a root token you
  choose (`root`, deliberately not secret — anyone can read it from the
  values file), and a KV v2 engine already mounted at `secret/`. Every
  restart of the pod wipes every value: fine for learning, disqualifying for
  anything else.
- The injector (mutates pods to add Vault sidecars) is disabled; ESO talks to
  Vault's API directly and needs no sidecar.

### Check

Both namespaces show their pods `Running`. `kubectl exec -n vault vault-0 --
vault status` (inside the pod, no token needed for `status`) reports
`Initialized: true`, `Sealed: false`.

## 9. Seed Vault and wire up the ExternalSecret

### Goal

`enjoythings-secret` populated by ESO from values living only in Vault.

### Steps

```sh
LLM_API_KEY=sk-your-real-key ./services/k8s/secrets/external-secrets/vault-seed.sh
kubectl apply -f services/k8s/secrets/external-secrets/vault-token-secret.yaml
kubectl apply -f services/k8s/secrets/external-secrets/secretstore.yaml
kubectl apply -f services/k8s/secrets/external-secrets/externalsecret.yaml
kubectl get externalsecret enjoythings-secret -n enjoythings
kubectl get secret enjoythings-secret -n enjoythings -o jsonpath='{.data}' | jq keys
```

### Why

- `vault-seed.sh` writes four fields — `JWT_SECRET`, `POSTGRES_PASSWORD`,
  `FRAUD_POSTGRES_PASSWORD`, `LOCAL_LLM_API_KEY` — to `secret/enjoythings`
  with `vault kv put`, which replaces the whole document. Only four values
  live in Vault; the two connection URLs are built later by the
  `ExternalSecret`'s template, so a password can never disagree with the URL
  that embeds it.
- `vault-token-secret.yaml` puts Vault's dev root token (`root`) into a
  Secret ESO reads to authenticate — safe to commit since dev mode's root
  token is already public in the values file. A real deployment uses
  Kubernetes auth instead (section 18).
- `secretstore.yaml` tells ESO how to reach Vault: address, KV mount path,
  auth token location. It is namespaced (`SecretStore`, not
  `ClusterSecretStore`), so only `ExternalSecret`s in `enjoythings` may use it.
- `externalsecret.yaml` pulls all four Vault fields into the Secret
  (`dataFrom`/`extract`), then templates the two connection-URL keys from
  them (`mergePolicy: Merge` keeps both; the default, `Replace`, would drop
  the four extracted keys). `creationPolicy: Owner` means ESO creates the
  Secret, recreates it if deleted, and deletes it if the `ExternalSecret` is
  deleted — the same "exactly one owner" contract from section 2, now held
  by ESO.
- `refreshInterval: 30s` is short on purpose, so section 10's rotation is
  quick to watch. A production value is commonly `1h`.

### Check

`kubectl get externalsecret` shows `STATUS: SecretSynced`. The Secret has the
same six keys as always, and `kubectl get secret enjoythings-secret -n
enjoythings -o jsonpath='{.data.JWT_SECRET}' | base64 -d` prints the value
you seeded.

## 10. Rotate a value in Vault and watch it flow through

### Goal

See a credential change with no `kubectl apply`, no `kubeseal`, no git
commit at all — the point of keeping the value out of git entirely.

### Steps

```sh
NEW_JWT=$(openssl rand -hex 32)
kubectl exec -n vault vault-0 -- sh -c "
  VAULT_TOKEN=root vault kv patch -mount=secret enjoythings JWT_SECRET='$NEW_JWT'
"
watch -n5 "kubectl get secret enjoythings-secret -n enjoythings \
  -o jsonpath='{.data.JWT_SECRET}' | base64 -d; echo"
```

Within `refreshInterval` (30s), the printed value changes. Then:

```sh
kubectl rollout restart deployment -n enjoythings
```

### Why

- `vault kv patch` (unlike `vault kv put`, used to seed) changes only the one
  named field, leaving `POSTGRES_PASSWORD`, `FRAUD_POSTGRES_PASSWORD` and
  `LOCAL_LLM_API_KEY` exactly as they were. This is the write you would
  reach for to rotate one credential in a real Vault too.
- ESO's controller polls Vault on `refreshInterval` and, seeing a changed
  value, rewrites the `Secret` object. No human, script, or `kubectl apply`
  is involved — this is the core advantage of ESO over Sealed Secrets: the
  cluster is a live mirror of the external store instead of a one-time
  encrypted snapshot.
- Rewriting the `Secret` object does not restart any pod. Exactly as with
  Sealed Secrets in section 7, `envFrom` environment variables are read once
  at container start, so a rollout restart is what actually makes running
  processes observe the new value.

### Check

The watched value changes within roughly 30 seconds of the `patch`, with no
git or kubectl-apply action of your own in between. After the rollout
restart, a pod's environment reflects the new value.

## 11. Generate an age key and configure SOPS

### Goal

An age keypair in the place SOPS expects it, and `.sops.yaml` pointing at
your public key.

### Steps

```sh
cd services/k8s/secrets/sops
./setup-age-key.sh
```

Copy the printed public key (`age1...`) into `.sops.yaml`, replacing
`age1REPLACE_WITH_YOUR_PUBLIC_KEY_FROM_SETUP_AGE_KEY_SH`.

### Why

- age keypairs have two halves. The public key (recipient), starting
  `age1...`, is safe for anyone to have — it can only encrypt. The private
  key (identity), starting `AGE-SECRET-KEY-1...`, can decrypt and must never
  be committed; `setup-age-key.sh` writes it to
  `~/Library/Application Support/sops/age/keys.txt` on macOS or
  `~/.config/sops/age/keys.txt` on Linux — both outside this repository, so
  no `.gitignore` entry is needed for it.
- `setup-age-key.sh` is idempotent: if the key file already exists it prints
  the existing public key instead of overwriting the private key, so
  re-running it (or a teammate running it on a shared machine by mistake)
  cannot destroy a key that ciphertext already depends on.
- `.sops.yaml`'s `creation_rules` picks a rule by matching the path of the
  file being encrypted. `path_regex: values-secrets.*\.yaml$` matches both
  `values-secrets.yaml` (the plaintext you edit) and
  `values-secrets.enc.yaml` (the ciphertext you commit) — SOPS uses the input
  file's path when you run `sops encrypt in > out`, so the rule only ever
  needs to match the input side.
- `encrypted_regex` restricts encryption to the leaf keys that actually hold
  a credential (`password`, `jwtSecret`, `databaseUrl`, `fraudDatabaseUrl`,
  `localLLMApiKey`). Every other key — chart structure, `secrets.create`,
  resource names — stays in the clear, so `git diff` on the encrypted file
  still shows meaningful structure instead of an opaque blob.
- A real team adds one `age` line per teammate (and one for a CI key) to
  `creation_rules`; SOPS encrypts the data key to every listed recipient, so
  any one of their private keys can decrypt.

### Check

`age-keygen -y <key file>` prints the same public key now in `.sops.yaml`.
`grep age1 .sops.yaml` no longer shows the placeholder.

## 12. Encrypt, decrypt, and deploy with `helm secrets`

### Goal

A committed, encrypted values file, and a `helm upgrade` that transparently
decrypts it.

### Steps

```sh
cd services/k8s/secrets/sops
cp values-secrets.example.yaml values-secrets.yaml   # git-ignored, fill in real values
sops encrypt values-secrets.yaml > values-secrets.enc.yaml
git add values-secrets.enc.yaml
rm values-secrets.yaml   # or keep it locally; only the .enc file is committed

helm secrets upgrade enjoythings services/charts/enjoythings \
  -n enjoythings -f values-secrets.enc.yaml
```

### Why

- `values-secrets.yaml` is git-ignored by the repository's own `.gitignore`
  (`values-secrets.yaml`) precisely so it can never be committed by
  accident; only `sops encrypt ... > values-secrets.enc.yaml` is meant to
  leave your disk for git.
- With this approach the chart keeps rendering its own Secret
  (`secrets.create: true`, the default) — the values file itself carries the
  credentials, just encrypted at rest in git, unlike Sealed Secrets or ESO
  where something external produces the `Secret` object directly.
- `sops encrypt` reads `.sops.yaml`, matches the `values-secrets.*\.yaml$`
  rule, encrypts every field matching `encrypted_regex` to your age public
  key, and writes a file that is valid YAML with `ENC[...]` values in place
  of the plaintext plus a `sops:` metadata block recording which recipients
  can decrypt it.
- `helm secrets upgrade` is the already-installed `helm-secrets` plugin's
  wrapper around `helm upgrade`: before invoking Helm, it finds every
  `-f`/`--values` argument that is SOPS-encrypted, decrypts it to a temporary
  file using your local age private key (or whichever key backend
  `.sops.yaml` names), passes the temporary plaintext to the real `helm
  upgrade`, and removes the temporary file afterward. The plaintext exists on
  disk only for the duration of that one Helm invocation, in a
  plugin-managed temp directory, never in your working tree.
- Because decryption happens locally, at the moment you run the command,
  **every teammate and every CI runner that needs to deploy must hold a
  private key SOPS encrypted to** — add their `age` recipient to
  `creation_rules` and re-encrypt (`sops updatekeys values-secrets.enc.yaml`)
  whenever the team changes.

### Check

`cat values-secrets.enc.yaml` shows `ENC[AES256_GCM,...]` values, not
plaintext. `sops decrypt values-secrets.enc.yaml` prints the original
plaintext back. `helm secrets upgrade` completes and
`kubectl get secret enjoythings-secret -n enjoythings -o jsonpath='{.data}' |
jq keys` shows the six keys.

## 13. Where SOPS stops working: Argo CD

### Goal

Understand why this approach, alone among the three, does not fit GitOps
cleanly — and what people do about it.

### Why

Argo CD's whole job is rendering git and applying the result with no human
in the loop, on a schedule, from inside the cluster. `helm secrets upgrade`
decrypts on your laptop, using a key that lives on your laptop, at the moment
you happen to type the command. Argo CD has neither a laptop nor your key, so
`helm secrets` is not something Argo CD can be told to run as part of a sync.
Three ways teams close this gap, in increasing order of effort:

1. **A CI pipeline decrypts and applies.** GitHub Actions (or similar) holds
   an age private key as a CI secret, runs `helm secrets template` (or
   `upgrade`) itself, and applies the *rendered* manifest — bypassing Argo
   CD's git-watching for this one object, or pushing the rendered plaintext
   Secret to a separate, access-restricted, short-lived branch Argo CD syncs
   from. This reintroduces "plaintext exists somewhere," now in CI's memory
   instead of your laptop's — smaller blast radius, but not zero.
2. **The Argo CD `helm` config management plugin.** Argo CD's `repo-server`
   can be configured to shell out to `helm secrets template` itself as part
   of rendering the source, if the `repo-server` pod is given the age
   private key as a mounted Secret. This makes Argo CD do the decrypting, at
   the cost of putting a decryption key inside the cluster's own control
   plane — which is exactly the kind of thing Sealed Secrets and ESO are
   designed to avoid needing.
3. **Do not use SOPS for anything Argo CD manages.** Many teams that adopt
   SOPS restrict it to values Argo CD never touches directly: Terraform
   variables, CI secrets, developer `.env` files, one-off scripts. For
   anything Argo CD deploys, they pick Sealed Secrets (ciphertext Argo CD can
   sync as-is) or ESO (Argo CD never sees the credential at all). This
   runbook's own `values-secrets.enc.yaml` is deliberately consumed by
   `helm secrets upgrade` run by a human or CI, not by an Argo CD
   `Application` — see the comparison in section 17 for why.

### Check

You can explain, without looking it up, why `git push` alone is not enough to
get a SOPS-encrypted value into a running Secret, unlike Sealed Secrets and
ESO, both of which reach a running Secret from git or an external store with
no laptop involved after the initial sync is wired up.

## 14. Hands-on practice

### Goal

Exercise the properties that make each tool different, not just the happy
path.

### 14a. Prove a SealedSecret is bound to its scope

```sh
cd services/k8s/secrets/sealed-secrets
sed 's/name: enjoythings-secret/name: some-other-name/' manifests/enjoythings-sealedsecret.yaml \
  | kubectl apply -f -
kubectl get secret some-other-name -n enjoythings
```

`strict` scope means the ciphertext was bound to the exact name
`enjoythings-secret`. Renaming the `SealedSecret` produces a controller log
entry like `no key could decrypt secret` and no `Secret` is ever created.
Delete the renamed object afterward.

### 14b. Prove ESO, not you, is keeping the Secret alive

```sh
kubectl delete secret enjoythings-secret -n enjoythings
kubectl get secret enjoythings-secret -n enjoythings -w
```

Within seconds the Secret reappears with the same values, recreated by ESO
because of `creationPolicy: Owner`. Contrast with Sealed Secrets: delete the
`Secret` there and the *SealedSecret* is what regenerates it via the
controller's own reconcile loop — same effect, different mechanism, both
because something in the cluster, not git, owns the object.

### 14c. Break the ExternalSecret on purpose and read the status

```sh
kubectl patch secretstore vault-dev -n enjoythings --type merge \
  -p '{"spec":{"provider":{"vault":{"server":"http://vault.vault.svc.cluster.local:9999"}}}}'
kubectl get externalsecret enjoythings-secret -n enjoythings
kubectl describe externalsecret enjoythings-secret -n enjoythings
```

The status flips away from `SecretSynced` and `describe` shows a connection
error. The existing `Secret` is left untouched — ESO never deletes a Secret
just because it can no longer reach the store, another reason
`creationPolicy: Owner` is safer than it sounds. Revert the patch (port
`8200`) and watch it recover on the next `refreshInterval`.

### 14d. Compare git history for the three approaches

```sh
git log --oneline -p -- services/k8s/secrets/sealed-secrets/manifests/enjoythings-sealedsecret.yaml | head -60
git log --oneline -p -- services/k8s/secrets/sops/values-secrets.enc.yaml | head -60
```

For Sealed Secrets, every rotation is a full-file diff of unrelated-looking
ciphertext (`seal.sh` re-encrypts everything, not just the changed field).
For SOPS, encrypting just the JWT secret and leaving the rest alone produces
a diff touching only the one `ENC[...]` value, plus a `lastmodified`/`mac`
change in the trailing `sops:` block — you can tell *which field* rotated
without decrypting anything. Neither is possible with ESO: nothing in git
changes at all when you rotate a value in Vault, which is the point.

## 15. Troubleshooting

| Symptom | Meaning | What to do |
| --- | --- | --- |
| `kubeseal`: `cannot fetch certificate ... connection refused` | No cluster reachable, or wrong context. | `kubectl config current-context`; or fetch a certificate once with `--fetch-cert > pub.pem` and pass `KUBESEAL_CERT=pub.pem` to `seal.sh` to seal offline. |
| Controller logs `no key could decrypt secret` | Sealed for a different controller instance, or name/namespace/scope mismatch. | Re-run `seal.sh` against the current cluster. The private key never survives `helm uninstall` + reinstall unless its Secret was backed up (section 16). |
| `kubeseal --fetch-cert` fails after install | `fullnameOverride` not applied, or wrong namespace. | `kubectl get deploy -n kube-system` — must be named `sealed-secrets-controller`. Reinstall with `values.yaml` if not. |
| `ExternalSecret` `SecretSyncedError`: connection refused | Vault address wrong, or the Vault pod is not `Running`. | `kubectl get pods -n vault`; confirm `secretstore.yaml`'s `spec.provider.vault.server`. |
| `ExternalSecret` `SecretSyncedError`: permission denied | Token in `vault-token-secret.yaml` does not match Vault's current root token. | Reseed with `vault-seed.sh`; confirm `vault-values.yaml`'s `devRootToken` matches. |
| ESO Secret has stale values after `vault kv patch` | `refreshInterval` has not elapsed, or the field name is wrong. | Wait one interval; `kubectl describe externalsecret` shows last sync time. Field names are exact-match. |
| `sops encrypt` says `config file not found` | No `.sops.yaml` above the current directory, or the path does not match `path_regex`. | Run from `services/k8s/secrets/sops/`. |
| `sops decrypt`/`helm secrets`: `age: no identity matched any of the recipients` | Your private key is not at `SOPS_AGE_KEY_FILE`, or you are not a listed recipient. | `age-keygen -y <key file>` and compare to `.sops.yaml`'s `age:` line; ask the encryptor to add your key and run `sops updatekeys`. |
| `helm secrets` fails to load the plugin (error mentions `platformCommand`/`command`) | A very new Helm release loads `plugin.yaml` more strictly than the plugin expects. | Local tooling mismatch, not a problem with the encrypted files — `sops encrypt`/`sops decrypt` run directly still work. Pin Helm to a version the plugin supports, or reinstall the plugin. |
| `terraform apply` in `20-platform` reverts your Sealed Secrets/ESO-owned Secret | Stage 20's `kubernetes_secret_v1.app` still exists and fights the other owner. | Section 2: `terraform -chdir=infra/terraform/20-platform destroy -target=kubernetes_secret_v1.app`. |
| SealedSecret Application stuck `OutOfSync` | The manifest was regenerated locally but never pushed. | Argo CD reads git, never your working tree — `git push`. |

## 16. Cleanup

```sh
# Sealed Secrets
kubectl delete -f services/k8s/secrets/sealed-secrets/argocd-application.yaml
helm uninstall sealed-secrets -n kube-system

# External Secrets Operator + Vault
kubectl delete -f services/k8s/secrets/external-secrets/externalsecret.yaml
kubectl delete -f services/k8s/secrets/external-secrets/secretstore.yaml
kubectl delete -f services/k8s/secrets/external-secrets/vault-token-secret.yaml
helm uninstall vault -n vault && kubectl delete namespace vault
helm uninstall external-secrets -n external-secrets && kubectl delete namespace external-secrets

# SOPS: nothing runs in the cluster to remove. Locally:
rm -f services/k8s/secrets/sops/values-secrets.yaml   # if you kept the plaintext copy
# The age private key at ~/Library/Application Support/sops/age/keys.txt (or
# ~/.config/sops/age/keys.txt on Linux) is yours to keep or remove; removing
# it makes every file encrypted to that key unrecoverable unless another
# recipient's key also exists.

# Whichever Secret is left standing
kubectl delete secret enjoythings-secret -n enjoythings
```

Uninstalling the Sealed Secrets controller **destroys its private key**
unless you backed up the Secret holding it (`kubectl get secret -n
kube-system -l sealedsecrets.bitnami.com/sealed-secrets-key -o yaml`, before
uninstalling). Without that backup, every `SealedSecret` ever sealed against
this cluster becomes permanently undecryptable — not a Sealed Secrets bug,
the entire point of the design.

## 17. Comparison: which one to pick

| | Sealed Secrets | ESO + Vault (or a cloud secret manager) | SOPS + age |
| --- | --- | --- | --- |
| Where the real credential lives | Encrypted, in git | In the external store, never in git | Encrypted, in git |
| What Argo CD syncs | Ciphertext it applies as-is | An `ExternalSecret` pointer, not the credential | Nothing directly (section 13) |
| Rotation | Re-seal and commit | Change the value in the store; the cluster catches up | Re-encrypt, commit, redeploy by hand or CI |
| Needs a running operator in-cluster | Yes (the controller) | Yes (ESO), plus the store itself | No |
| Needs a decryption key on every deployer/CI runner | No — only the cluster can decrypt | No — a ServiceAccount/IAM role authenticates instead | Yes |
| Fits GitOps (Argo CD) end-to-end, no side channel | Yes | Yes | No (section 13) |
| Blast radius of a leaked key | One cluster's SealedSecrets | Scoped by the store's own IAM/ACL | Every file ever encrypted to that recipient |
| Audit trail for who changed what, when | Git history + controller logs; ciphertext diffs are opaque | The store's own audit log | Git history; diffs show exactly which field changed |
| Good fit for | Small teams, no secret manager, everything in git | Teams with (or willing to run) a secret manager; values that must rotate with no deploy | Mostly-config values files with a few secret fields, applied by a human/CI, not Argo CD |
| Cloud equivalent | Same tool, same workflow | Vault dev → real Vault, or ESO's native AWS/GCP/Azure provider with IAM auth | Same tool; age recipients become the real team, or swap in a KMS backend |

For this repository specifically: if you already run the Terraform stages,
prefer ESO once you have (or are willing to run) any external secret store —
it is the only approach where rotating a credential requires no git
operation and no redeploy at all. Reach for Sealed Secrets when you want
everything, secrets included, resolvable from git alone with no extra moving
part running in the cluster. Reserve SOPS for values that are mostly ordinary
configuration with a handful of secret fields and that a human or CI
pipeline — not Argo CD — is the one applying.

## 18. Toward production

Everything above runs safely on a laptop. Moving any of it onto a real cloud
changes these things and nothing else:

1. **Vault dev mode becomes a real Vault, or the cloud's own store.** Replace
   `server.dev.enabled` with a proper `ha`/Raft configuration and auto-unseal
   via a cloud KMS key, or skip Vault entirely and point `secretstore.yaml` at
   ESO's native `aws.SecretsManager`, `gcpsm`, or `azurekv` provider — the
   `ExternalSecret` resource shape barely changes, only `spec.provider`.
2. **Token auth becomes IAM-scoped auth.** `vault-token-secret.yaml`'s root
   token was fine because dev mode's root token is public knowledge. A real
   deployment authenticates ESO with Kubernetes auth (Vault verifies the
   calling pod's ServiceAccount token against the API server, no static
   credential to leak) or, on a managed store, an IAM role attached to ESO's
   ServiceAccount (IRSA on EKS, Workload Identity on GKE). Either way, no
   long-lived secret sits in a Kubernetes Secret to authenticate with another
   secret.
3. **The Sealed Secrets controller's key needs a backup and rotation plan.**
   Losing the cluster without a backup of the controller's key Secret makes
   every committed `SealedSecret` permanently undecryptable — worth treating
   like a database backup, not an afterthought. The controller also supports
   periodic automatic key rotation; a real deployment turns it on rather than
   relying on one keypair forever.
4. **age recipients become the real team, and SOPS gains a KMS backend
   option.** `.sops.yaml`'s `creation_rules` grows one `age` entry per
   engineer and one for CI, or switches to `--kms`/`--gcp-kms`/`--azure-kv`
   so decryption is gated by cloud IAM instead of a file on someone's laptop
   — closing the "private key on a laptop" gap section 13 describes, though
   the GitOps gap (nothing decrypts on Argo CD's behalf automatically) stays
   regardless of key backend.
5. **State stops holding secrets.** If you provisioned any of this with
   Terraform (`infra/terraform/26-secrets`), a remote backend with encryption
   at rest replaces the local `terraform.tfstate` files — the same move the
   Terraform runbook's own section 11 describes for stage 20.
6. **All three tools run the same in CI as on a laptop.** `helm template`
   with the chart's third-party values, `sops decrypt --extract` for a
   pipeline that needs one field, and `kubeseal --validate` are all
   scriptable and belong in the same CI pipeline that already runs
   `terraform validate` and `helm lint`.
