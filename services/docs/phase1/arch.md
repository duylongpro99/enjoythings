## 3. Layer responsibilities

### Handler
- Parse and validate HTTP request (body, path params, headers)
- Extract `user_id` from JWT claims (injected by middleware)
- Call the service layer
- Map service errors to HTTP status codes
- No business logic lives here

### Service
- Enforce business rules (non-negative balance, matching wallet ownership)
- Coordinate DB operations — transfers must debit and credit in one transaction
- Return domain errors (`ErrInsufficientFunds`, `ErrWalletNotFound`)

### Repo
- Generated by `sqlc` from SQL query files
- Thin wrappers around `pgx` connection pool
- Accepts `pgx.Tx` for transactional operations

### Domain
- Plain Go structs for `Wallet`, `Transfer`, `LedgerEntry`
- Balance invariant enforced as a method: `wallet.Debit(amount) error`
- No DB or HTTP imports in this package

## 4. Database schema

```sql
-- wallets
CREATE TABLE wallets (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     UUID NOT NULL,
  balance     BIGINT NOT NULL DEFAULT 0,  -- cents
  currency    CHAR(3) NOT NULL DEFAULT 'USD',
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT non_negative_balance CHECK (balance >= 0)
);

-- transfers
CREATE TABLE transfers (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  from_wallet_id  UUID NOT NULL REFERENCES wallets(id),
  to_wallet_id    UUID NOT NULL REFERENCES wallets(id),
  amount          BIGINT NOT NULL CHECK (amount > 0),
  status          TEXT NOT NULL DEFAULT 'completed',
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ledger_entries
CREATE TABLE ledger_entries (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  wallet_id    UUID NOT NULL REFERENCES wallets(id),
  transfer_id  UUID NOT NULL REFERENCES transfers(id),
  direction    TEXT NOT NULL CHECK (direction IN ('debit', 'credit')),
  amount       BIGINT NOT NULL CHECK (amount > 0),
  balance_after BIGINT NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Key decisions:
- `balance` has a `CHECK (balance >= 0)` constraint as a last-resort safety net at the DB level
- All amounts in cents (`BIGINT`) — no `NUMERIC` or `FLOAT`
- Ledger stores `balance_after` for point-in-time balance reconstruction

## 5. Transfer flow

```
POST /v1/transfers
  │
  ├─ Handler: parse body, validate amount > 0
  │
  ├─ Middleware: extract user_id from JWT
  │
  ├─ Service.Transfer(ctx, fromID, toID, amount):
  │    ├─ BEGIN TRANSACTION
  │    ├─ SELECT wallet FOR UPDATE (lock both rows)
  │    ├─ Check from.balance >= amount
  │    ├─ UPDATE wallets SET balance = balance - amount WHERE id = fromID
  │    ├─ UPDATE wallets SET balance = balance + amount WHERE id = toID
  │    ├─ INSERT INTO transfers ...
  │    ├─ INSERT INTO ledger_entries (debit) ...
  │    ├─ INSERT INTO ledger_entries (credit) ...
  │    └─ COMMIT
  │
  └─ Handler: return 200 with transfer + new balances
```

The `SELECT ... FOR UPDATE` on both wallet rows prevents concurrent transfers from producing race conditions. Rows are always locked in consistent ID order (lower UUID first) to prevent deadlocks.

## 6. JWT middleware

```go
// Pseudocode
func JWTMiddleware(secret string) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            token := extractBearerToken(r)
            claims, err := validateJWT(token, secret)
            if err != nil {
                http.Error(w, "unauthorized", 401)
                return
            }
            ctx := context.WithValue(r.Context(), ctxKeyUserID, claims.UserID)
            next.ServeHTTP(w, r.WithContext(ctx))
        })
    }
}
```

## 8. Testing strategy

| Layer | Approach |
|---|---|
| Domain | Pure unit tests — no mocks needed |
| Service | Unit tests with mock repo (`mockery` or hand-written interface mock) |
| Handler | Unit tests with `httptest.NewRecorder`, mock service |
| Integration | `testcontainers-go` spins up real Postgres — tests run full stack |

Integration test scope: the transfer happy path and the insufficient-funds error path are the minimum required integration tests.
