# Phase 5 Operability Debt

Problem: Phases 1-4 left three holes that only show up once the platform runs unattended. A saga that entered `FRAUD_REVIEW` had no exit — no event moves it out, and a payment result arriving during review is stored as a deferred terminal result and never applied — so a flagged payment held the payer's money indefinitely. Every Kafka consumer treated an unparseable payload as a deliberate skip and committed the offset, so a bad producer lost records with nothing but a log line left behind. And token verification only accepted a shared HMAC secret, which forces every service that verifies a token to also be able to mint one.

Structure: The review exit is two operator decisions on the orchestrator, `ResumeFraudReview` and `RejectFraudReview`, exposed as `ResumeFraudReview`/`RejectFraudReview` RPCs and as `POST /v1/payments/{id}/fraud-review/{resume,reject}` on the gateway, gated on the `role` claim already required in every token. Resume replays a stored deferred result through the normal `HandlePaymentCompleted`/`HandlePaymentFailed` path — the payment processor's event-ID prefix is what distinguishes the two — so a payment the rail already settled reaches its real end state instead of waiting for a redelivery that will never come; with nothing deferred the saga returns to `PAYMENT_PROCESSING`. Reject reuses `resumeCompensation`, the same path a rail failure takes, so a rejected payment is indistinguishable downstream apart from its `fraud_rejected` failure code. Both decisions write a `review_resumed`/`review_rejected` audit record naming the actor before anything else happens.

Poison records now go to a per-topic `<topic>.dlq` through `internal/deadletter`, publish first and commit second, so a broker outage retries the record instead of dropping it. The payload keeps the raw key and value as bytes — a poison record is not necessarily valid JSON, or even UTF-8 — alongside the topic, partition, offset, decode error, and failure time. The Python worker reaches the same topics through a `DEAD_LETTER` consumer decision handled by the Kafka runner, which owns the record coordinates the worker never sees.

Token verification moved behind an `auth.Verifier` pinned to one signing method, chosen by `JWT_ALG`. RS256 takes the issuer public key inline or from a mounted file; HS256 with `JWT_SECRET` stays the default so local development is unchanged.

Tradeoffs: Resume clears the deferred result before replaying it, so a replay that fails midway leaves the saga in `PAYMENT_PROCESSING` with the original event already committed in Kafka. The audit record carries the full deferred payload for exactly that case — recovery is a manual re-drive from the audit trail rather than an automatic one. Reject deliberately keeps the deferred result on the saga instead: it records what the rail actually did, and clearing it would hide that.

Dead-lettering is per-consumer rather than a shared middleware because each consumer decides for itself what counts as unparseable, and that judgment is the part worth keeping local. A nil publisher falls back to the old log-and-commit behavior so in-process test harnesses need no broker; the Kafka constructors always wire a real one, which is the only path that runs in production.

The gateway admin routes are guarded by a role claim on the same token the payer uses, not by a separate operator identity. That is the smallest change that closes the hole, and it is the reason the audit record stores the acting user ID: the trail, not the transport, is what makes the decision attributable. mTLS between services remains out of scope and is tracked in `docs/phase5/backlog.md`.
