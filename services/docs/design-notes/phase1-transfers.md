Problem: Phase 1 transfers must move money between two wallets without allowing partial balance changes, ownership leaks, deadlocks, or ledger gaps.
Structure: Keep the HTTP handler responsible for JSON shape, UUID parsing, and cheap request validation. Keep the wallet service as the business facade used by routing. Keep the Postgres repository method responsible for the database transaction because it owns the concrete row locks, balance updates, transfer insert, ledger inserts, commit, and rollback behavior in one place.
Tradeoffs: A separate transfer service package would match the architectural wording more literally, but the current monolith already exposes a small wallet.Store interface and a centralized repository transaction. Adding a new package now would increase churn without improving the Phase 1 behavior; the boundary can still split cleanly later because callers depend on the service interface rather than direct SQL.
