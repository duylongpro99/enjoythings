# Phase 5 Operator Review UI

Problem: Phase 5 gave a saga held in `FRAUD_REVIEW` an exit — `ResumeFraudReview` and `RejectFraudReview` — but only as REST calls an operator had to aim by hand. Nothing listed which payments were waiting or for how long, and the verdict that held a payment (session, action, risk score, reason) lived only in the saga row and the `saga_fraud_audit_records` table, both reachable only through the database. An operator deciding a review could not see what the fraud worker concluded, what had already been decided on the payment, or whether the rail had settled it during the hold.

Structure: Two read paths were added beside the decisions and follow them exactly. The orchestrator gains `ListFraudReviews`, the queue, backed by one new `Store` method, `ListFraudReview`, which selects `state = 'FRAUD_REVIEW'` ordered by `fraud_flagged_at` — a subset of the non-terminal partial index, so no new index on `sagas`. It also gains `GetFraudReview`, the saga with its audit trail; the trail read sits on an optional `auditTrailStore` interface mirroring `auditStore`, so a store that cannot persist a trail returns none instead of failing, and the phase 4 test harness keeps satisfying `auditStore` unchanged. The detail is not limited to sagas still under review: the trail is how a past decision is explained, so a decided payment stays readable. `saga_fraud_audit_records` gets a `(payment_id, created_at)` index (migration `000011`) because the detail reads one payment's whole trail in order.

On the wire, `PaymentSaga` grows `user_id`, the verdict fields, and `deferred_payment_json`, so the two new RPCs `ListFraudReviews` and `GetFraudReview` reuse the saga message and `sagaMessage`/`sagaFromMessage` stay a faithful pair; `FraudAuditRecord` is the only new message. The gateway exposes them as `GET /v1/fraud-reviews` and `GET /v1/fraud-reviews/{payment_id}` in a dedicated handler gated on the same `admin` role as the decisions, and embeds an audit record's `details_json` as JSON when it parses so a client reads structured fields. The response says whether a deferred rail result is waiting rather than echoing it; the `deferred_terminal` audit record already carries the payload.

The page at `/admin/fraud-reviews` in `web/` lists the queue, shows one review's facts and trail, and offers Resume/Reject with a reason. It reaches the gateway through a Next route handler under `/api/admin/fraud-reviews/*` that forwards the pasted admin bearer token: the gateway has no CORS handling and sits on another origin, and `/api/chat` already fronts FastAPI the same way. The proxy knows exactly three route shapes and answers 404 for anything else, so it cannot become a general tunnel to the gateway.

Tradeoffs: The "enrichment that produced a verdict" is split across two databases. The saga side holds the verdict itself — session ID, action, risk score, reason, the `transition` audit record, and any deferred rail result — and that is what the page shows. The velocity metrics, sanitized facts, and raw model response stay in the fraud worker's `fraud_sessions` table (`enrichment_json`, `sanitized_facts_json`, `raw_llm_response`), keyed by the `fraud_session_id` the page displays. Surfacing them would mean the orchestrator opening a second database or the gateway calling a new Python endpoint, both a service boundary crossed for read-only display; the session ID is the deliberate join key and the deeper enrichment stays a lookup in the fraud database.

Reviewer assignment was skipped. Nothing in the saga row models an assignee, and adding one is a write path with its own audit semantics rather than something that falls out of a queue view. The admin token is pasted into the page and held only in component state; there is no session layer, so the operator identity the audit trail records is the one on the token. Widening `PaymentSaga` means every saga response now carries fraud metadata to the gateway, which is the trusted party that already receives the whole saga; the payer-facing `GET /v1/payments/{id}` response is unchanged. The queue is unpaginated: a review queue long enough to need paging is an operational problem before it is a UI one, and the review-deadline reaper in the backlog is the intended answer to a growing queue.
